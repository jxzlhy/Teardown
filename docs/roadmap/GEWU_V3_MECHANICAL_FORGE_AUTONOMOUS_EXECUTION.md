# 0. 给执行 AI 的最高优先级指令

你现在接管的是一个正在持续演进的真实项目。你的任务不是只实现下面列出的功能，也不是完成 V3.0 标题下的事项就结束。

**你必须把自己作为项目的长期技术负责人、产品负责人、3D 技术美术、测试工程师和交付负责人来工作。**

从读取项目开始，持续执行以下循环：

1. 理解项目现状、技术基线、代码结构、已有能力和历史约定。
2. 检查当前版本实际运行效果，确认真实问题，不凭空假设。

10. 持续重复，直到本次运行的可用 Token、工具调用额度或执行环境确实无法继续，或者遇到必须由用户处理的硬阻塞。

不要把“本指令列出的任务完成”理解为“整个工作结束”。本指令是一个持续自主研发协议，不是一次性 TODO 清单。

# 2. 产品定位与边界

## 2.1 产品方向

本阶段为格物馆增加一个独立的虚拟机械创造系统：

**GEWU · MECHANICAL FORGE / 机械锻造所**

它让格物馆不仅能够展示现实中存在的机械和设备，还能够通过程序化建模创造现实中不存在、但具有机械结构可信度的虚拟机械。

本系统不是宇宙探索项目，不以行星、星云、宇宙世界观为方向。不要把项目带偏。

## 2.2 两种内容来源

格物馆未来可以同时管理：

1. **REAL OBJECTS / 真实物件**：来自真实产品、真实机械或经过整理的外部模型资源。
2. **GENERATED OBJECTS / 程序化创造物**：由 Mechanical Forge 根据参数、结构规则和生成器创造的模型。

两类模型尽可能接入同一套展示、选择、旋转、缩放、拆解、零件说明和展品管理能力。

## 2.3 本阶段不做什么

- 不把一张 AI 图片伪装成真正的 3D 模型。
- 不把一个球体或几个基础几何体堆叠起来就称为完整发动机。
- 不把随机拼接当作机械生成。
- 不引入必须联网才能工作的生成服务作为核心依赖。
- 不擅自引入收费 API、云端服务或用户未授权的外部服务。
- 不为追求效果而破坏现有项目稳定性。
- 不虚构机械的工程性能、真实可制造性或物理参数。
- 不将概念演示误标为真实工程设计。

程序化生成应优先在本地浏览器或项目既有运行环境中完成。若发现确实需要外部工具（例如 Blender 离线建模流水线），先评估本机环境和项目部署方式，再决定是否引入；不能让项目运行依赖用户并未安装的工具。

# 3. V3.0 核心目标与交付标准

V3.0 的目标不是一次性实现所有机械类别，而是建立可扩展的生成框架，并完成一个足够扎实的标杆模型。

## 3.1 核心系统

至少建立以下职责清晰的模块（实际命名服从现有项目规范）：

- Generator Core：生成器注册、调度、参数校验和随机种子管理。
- Geometry Builders：机械几何构造器。
- Material System：金属、橡胶、塑料、陶瓷、玻璃、涂层等材质配置。
- Assembly System：零件、子装配体、父子层级、局部坐标和装配关系。
- Motion System：运动部件、运动约束和动画时间轴。
- Exploded View：爆炸拆解、复位、分层拆解。
- Metadata System：模型信息、零件名称、说明、参数和生成记录。
- Preview / Viewer Adapter：将生成模型接入格物馆现有 3D 展示系统。
- Export Adapter：在技术可行时导出 GLB/GLTF，并保留必要的层级、材质和动画。
- Validation：生成结果结构校验、尺寸校验、引用校验和基本质量检查。

不要为了照搬以上清单而制造过度抽象。模块要有真实职责，并能被测试。

## 3.2 第一批标杆对象

优先顺序：

### A. V8 内燃机（首个标杆）

目标是让用户能辨认出这是一台具有合理结构关系的 V8 发动机，而不是一个“发动机风格”的装饰模型。

建议逐步包含：
- 发动机缸体。
- 左右气缸列与气缸孔位。
- 活塞（8 个）。
- 连杆（8 个）。
- 曲轴及曲柄结构。
- 气缸盖。
- 凸轮轴（按选定结构配置）。
- 气门及弹簧（可分阶段实现）。
- 进气歧管。
- 排气歧管。
- 正时机构或外部传动机构。
- 油底壳、前端盖等外部构件。

注意：V8 有多种结构形式。先选定一种便于可视化的概念布局，并在模型说明中明确标注。不要把不同发动机布局混在一起，也不要将示意模型声称为可制造工程模型。

必须实现：
- 主要部件独立网格或合理的可选取节点。
- 零件命名和分组。
- 正确的初始装配位置。
- 可见的内部构造。
- 活塞与曲轴之间具有可理解的联动关系。
- 可播放、暂停、重置的基础运动演示。
- 爆炸拆解和复位。
- 零件点击/选中及信息展示。
- 生成参数与随机种子可复现。

### B. 涡扇发动机（第二标杆）

在 V8 的框架验证稳定后再做，不要与 V8 同时粗糙铺开。

建议结构：
- 进气口。
- 风扇级。
- 低压压气机。
- 高压压气机。
- 燃烧室示意结构。
- 高压涡轮。
- 低压涡轮。
- 核心机轴系。
- 外涵道。
- 短舱/外壳。
- 排气喷口。

要求能够通过分层剖切或爆炸拆解看清内部级次。叶片应体现环形分布、扭转趋势和合理的空间关系；不要只用平板圆片代替叶片。

### C. 科幻复合动力核心（创造性标杆）

这是检验系统能否“创造现实中不存在的机械”的关键对象。

要求：
- 有清晰的核心主体、支撑框架、能量/动力传递部件和外围机械结构。
- 具有一致的设计语言和明确的结构层级。
- 可以有非现实构造，但外观必须有机械逻辑。
- 各部件可独立选取、隐藏、拆解和说明。
- 动画必须体现结构关系，而非随意旋转所有零件。
- 清楚标注“虚构概念模型 / 非真实工程设备”。

# 4. 程序化生成系统设计

## 4.1 参数化，而不是纯随机

每个生成器应有明确参数 Schema，包括：
- 参数名称、类型、默认值。
- 最小值、最大值和步进。
- 单位。
- 参数说明。
- 参数之间的依赖关系。
- 不合法组合的处理方式。

随机性必须受 Seed 控制：
- 相同生成器版本 + 相同参数 + 相同 Seed，应尽可能得到一致结果。
- 不得依赖不可控的 `Math.random()` 作为唯一随机源。
- Seed、生成器版本和参数必须写入模型元数据。
- 参数变化应只影响相关结构，不应无故破坏其他部件。

## 4.2 几何质量

生成几何体时重点检查：
- 法线方向和法线平滑。
- 几何体封闭性（适用时）。
- 重叠面、穿插、闪烁和 z-fighting。
- 细节厚度与比例。
- 倒角、圆角和边缘处理。
- 叶片、齿轮、曲面等结构的形态质量。
- 细节密度与性能平衡。

避免：
- 过多无意义的细分。
- 依赖极高面数掩盖造型问题。
- 大量重复创建材质和几何体。
- 生成后无法释放的 GPU 资源。
- 只在单一视角看起来正确的模型。

## 4.3 材质与视觉语言

建立有限、统一、可复用的材质体系：
- 拉丝金属。
- 铸造金属。
- 阳极氧化金属。
- 镀铬金属。
- 橡胶。
- 工程塑料。
- 陶瓷。
- 玻璃/透明罩。
- 涂装表面。

材质应有粗糙度、金属度、颜色和适当的细节变化。不要所有零件都使用同一种高亮银色。

模型必须在项目实际灯光和环境下检查，避免过曝、过暗、塑料感过强或材质完全不可辨认。

# 5. 装配系统：让零件真正属于一台机械

## 5.1 数据结构要求

为生成对象建立统一、可序列化的结构描述。建议至少表达：

- Model：整机。
- Assembly：子装配体。
- Part：零件。
- Transform：位置、旋转、缩放。
- Material：材质引用。
- Geometry：几何引用或生成参数。
- Parent / Children：层级关系。
- Tags：分类、功能、可动、可拆等标签。
- Motion：运动定义。
- Explode：拆解偏移或拆解组。
- Metadata：名称、说明、版本、Seed、来源类型。

实际接口根据现有代码风格决定。不要只建立一份 JSON 外壳而没有真正用于渲染和交互。

## 5.2 坐标与装配

- 明确世界坐标、模型局部坐标、零件局部坐标。
- 明确模型中心、地面基准和默认朝向。
- 零件必须在正确位置装配，不能初始就漂浮、错位或裸露。
- 父子层级变化后必须重新验证世界变换。
- 缩放模型时，拆解距离和控制器目标应保持合理。
- 装配完成后进行整体包围盒和中心点校验。

## 5.3 零件身份

每个重要零件应有稳定 ID，不要只依赖显示名称或数组下标。
选择、隐藏、拆解、信息面板和导出都应引用同一身份标识。

# 6. 运动系统

先实现可解释、可复现的运动，不追求一开始就做完整物理仿真。

## 6.1 V8 运动

- 曲轴以稳定角速度旋转。
- 活塞沿各自气缸轴线往复。
- 连杆两端与活塞销、曲柄销保持视觉上的连接关系。
- 左右气缸列方向和夹角一致。
- 运动过程中不得出现明显脱离、穿模或抖动。
- 动画支持播放、暂停、重置和速度调节。
- 页面失焦或组件卸载时应妥善处理动画循环。

如果暂时使用运动学近似，必须在文档中说明，不得宣称已完成真实动力学仿真。

## 6.2 涡扇运动

- 风扇和压气机级按合理方向旋转。
- 同轴但属于不同轴系的部件应能体现不同转速关系（概念演示即可）。
- 不要让所有叶片、外壳和整个发动机一起无差别旋转。
- 动画应能暂停、重置和调速。

## 6.3 性能与生命周期

- 使用项目现有渲染循环，不要重复创建多个 RAF 循环。
- 组件卸载时清理事件监听、动画和 GPU 资源。
- 不可见或暂停时降低不必要的计算。
- 不要每帧创建大量临时对象。
- 对高频更新使用合适的缓存和对象复用。

# 7. 爆炸拆解与统一展品体验

尽量复用现有拆解系统，而不是另写一套互不兼容的实现。

至少支持：
- 整机视图。
- 一级子装配体拆解。
- 主要零件拆解。
- 单零件选中。
- 单零件隐藏/显示。
- 一键复位。
- 拆解进度控制（如果现有交互适合）。
- 零件信息展示。
- 选中状态与拆解状态一致。

拆解偏移必须依据零件空间位置、所属分组和模型尺寸计算，不能所有零件都沿同一个方向平移。

必须验证：
- 拆解后零件不会飞出不可见区域。
- 零件之间不会大量重叠。
- 复位后回到精确的初始装配位置。
- 连续拆解/复位不会累积偏移误差。
- 隐藏零件后再复位仍然正确。
- 选择零件后信息面板显示正确对象。

# 8. 用户界面与体验

新增 Mechanical Forge 入口时，先理解现有格物馆的视觉系统，不要另起一套风格。

UI 应围绕实际任务组织：
1. 选择机械类别。
2. 选择生成器。
3. 调整参数。
4. 生成或重新生成。
5. 查看模型。
6. 播放机械运动。
7. 拆解并检查零件。
8. 保存或导出。

界面至少考虑：
- 生成器选择区。
- 参数控制区。
- 主 3D 视图区。
- 模型信息/零件信息区。
- 运动控制区。
- 拆解控制区。
- 保存/导出操作。

要求：
