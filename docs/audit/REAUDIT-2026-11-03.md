### P0

**RS-01 · `/studio` 卸载不删 `window.__STUDIO`，每次再进净留存一整个场景**
- 证据：`src/studio/index.js:240` 写入钩子；`src/components/StudioView.vue:300` 卸载只调 `api.dispose()`，而 `api.dispose`（index.js:122 附近）只 `viewer.dispose()`。闭包链 `api → report → nodesByPath（全部 Object3D）→ 几何/贴图` + `workshop.history` 50 条命令闭包 + 已 dispose 的 renderer + 脱离 DOM 的 canvas（匿名 pointer 监听 `viewer.js:147-154` 不可移除）。
- 为什么是 P0：这与项目**上一轮刚刚修好并写进文档**的 `__ENGINE` 结论（`DeviceViewer.vue:1258` 注释原文："不删会让整棵已 dispose 的场景被 window 强引用"）是**同一个缺陷类别在新模块重演**；而项目提交信息里反复出现的"OOM 崩页 / load 15-25 持续 OOM"正是这类放大器最可能的受害者。
- 说明：另一路运行时探针（并行会话）在单轮访问下观察到"离开页面后 heap 确实被回收"，因此**代码泄漏 + 环境压力（并行会话/无头实例堆积）是叠加关系**，不是单一归因。这条我按"代码可消掉的放大器"记，不冒充已证明的唯一根因。
- 建议：`api.dispose` 内 `delete window.__STUDIO` + `workshop.dispose()` + `report = null`；canvas 监听改具名函数并 remove。成本：低。

## 四、我上一轮的两处测量错误（本轮自查纠正）

诚实记账——这两条都写进了上一轮的文档，需要以本文件为准修正：

1. **"星图页加载 three chunk"是误判**。原因：我的判定用 `filename.startsWith('three')`，命中了知识词条模块 `three-axis-gimbal.js`。用生产 `vite preview` 重测：**星图 5 块 JS，不含 three chunk**，`GraphView.vue:101-106` 也确实不 import three。→ 上轮"图谱页不加载 three"的设计目标**成立**。
2. **"Apollo 三件纹理 64547×… / 估算显存 34GB"是我的 JPEG 解析缺陷**。原因：marker 遍历未在 **SOS(0xDA)** 处停止，把熵编码数据里的字节对误读成 SOF 尺寸。修正解析器后实测：**最大边 2048、单台显存 129/50/64MB**（正常量级）。→ 真实问题不是"超大纹理"，而是**格式与压缩违规**（RS-08：JPEG 贴图 + `apollo-hatch` 未 DRACO）。

另需注意的口径限制（沿用上轮声明）：对比度扫描以"最近不透明祖先合成背景"为底，文字压在缩略图/画布上的情形**偏乐观**；显存为 RGBA8+MIP(×1.34) 估算，非真机计量。

**78 → 77**。分数微降的原因不是"新模块做得差"——`/studio` 的分层、真实性口径、单测与验证护栏在同类增量里属于高水准；降的是**两类信号**：
